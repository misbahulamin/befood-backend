## ADDED Requirements

### Requirement: Shared public_id field shape

Every resource that adopts public UUID identity SHALL keep its integer primary key for database relations and SHALL add a non-editable unique indexed `public_id` UUID generated by default on create. Existing rows MUST be backfilled without deleting or recreating data.

#### Scenario: New row gets public_id

- **WHEN** a new row is created for a resource that uses public UUID identity
- **THEN** the row has a generated unique `public_id` without the client supplying it

#### Scenario: Existing rows backfilled

- **WHEN** the public UUID migration runs for a model with existing rows
- **THEN** each row retains its integer PK and receives a unique non-null `public_id`

### Requirement: Customer serializers hide integer PK

For resources with `public_id`, customer-facing and public API responses MUST expose `public_id` as the resource identity and MUST NOT expose the integer primary key as `id`. Nested references MUST use `{resource}_public_id` naming.

#### Scenario: Customer payload uses public_id

- **WHEN** a customer client retrieves a public-UUID resource
- **THEN** the payload includes `public_id` and does not include integer `id`

### Requirement: Lookup uses public_id

Detail and nested action URLs for public-UUID resources MUST resolve by `public_id`. Integer path segments MUST NOT successfully identify those resources after cutover.

#### Scenario: Integer path fails after cutover

- **WHEN** a client requests a former integer identity path for a cut-over resource
- **THEN** the system returns not-found rather than the resource

### Requirement: Admin may keep internal integer FKs in filters

Admin-only filter query parameters MAY continue to accept integer foreign keys for internal ops tooling until that admin surface is explicitly migrated. Customer surfaces MUST NOT rely on those integer filters.

#### Scenario: Admin filter still integer while customer uses UUID

- **WHEN** an admin list filter uses an integer meal/plan FK that has not been migrated in an ops phase
- **THEN** the filter may still work for managers while customer meal identity remains UUID-only
